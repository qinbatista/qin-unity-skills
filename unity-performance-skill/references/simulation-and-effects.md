# Simulation and effects in 2D games

Start with one busy moment in the game. Count active and visible objects, identify which objects can affect each other, and name the gameplay result that must survive culling or reduced visual quality. Choose simulation, collision detection and rendering separately. Compare candidates at the same density, camera, tick rate and target hardware.

## Choose the simulation owner

| Workload | Starting point | Evidence that would change the choice |
| --- | --- | --- |
| A few individually authored characters with input, Animator, colliders or complex lifecycles | GameObjects with the existing Controllers. | A trace shows repeated numerical work across characters dominates. Extract that calculation first. |
| Many independently tracked projectiles or enemies obey similar rules | Process the active records together. Consider Entities when several systems repeatedly query common component data and can work on chunks. | Check the cost of spawning, structural changes and copying transforms to presentation. Compare the full frame with the simpler collection. |
| A crowd tracks the same player | Snapshot the player position once per simulation tick. Each agent reads that sample and writes its own result. A CPU Job with Burst can serve existing GameObjects or an ECS system. | Measure scheduling, wait and publication time together. A small loop may already fit the budget. |
| Agents interact with nearby peers | Generate candidate neighbors spatially, then evaluate actual pairs. For parallel updates, read the previous state and write individual outputs or reduce pair contributions in a defined order. | Compare candidates per tick, dense clusters, missed contacts and gameplay outcomes at cell boundaries. |
| Dust, leaves or sparks react visually to a character | Feed position, velocity or impact events into a batched effect. Use GPU VFX Graph where the actual renderer, graphics API and device support it. Select an existing compatible particle backend when the project permits it. | A collectible, damaging projectile or quest object needs CPU-owned identity and outcomes. Its appearance can still be batched. |

ECS organizes gameplay data. Jobs schedule CPU work, and Burst compiles supported code. These choices can be combined independently of GPU particle simulation. With complex characters, keep the authored presentation and physics interfaces they need and move only the measured shared work. Follow the existing completed-batch contract for native data ownership and Controller updates. ## Choose a collision model

- **Proximity, attraction or targeting.** For a single player and a modest active set, a squared-distance check may suffice. At higher density, use the existing spatial index or physics broadphase. Query neighboring cells within the full interaction radius, then check exact distance. For fast-moving objects, test the swept path when a hit could fall between ticks.
- **Solid contact, bounce, joints or terrain.** For a game whose characters and terrain use `Rigidbody2D` and `Collider2D`, stay in the same Physics2D world. Filter layers and choose simple shapes. Verify collision response at the game's fixed timestep. [Unity physics engines](https://docs.unity3d.com/6000.0/Documentation/Manual/PhysicsSection.html)
- **Large simulated populations.** Evaluate the pinned editor's low-level 2D physics API (PhysicsCore2D) if a dedicated 2D world suits the workload. It needs its own bodies, shapes, queries and contact handling. It cannot collide directly with the game's built-in `Collider2D` instances. Entities projects already using the 3D `com.unity.physics` solver may constrain motion to a plane when those contact semantics fit. Check moving characters against the real ground and against one another before migrating. [Unity low-level 2D physics](https://docs.unity.com/en-us/engine/6000.3/manual/unity2d/2d-physics-api/get-started/introduction) · [Unity Physics package](https://docs.unity3d.com/Packages/com.unity.physics@1.3/manual/index.html)

## Simplify a ground pickup

If the design calls for a coin to hop, settle and fly to the player along a known path, animate its presentation. Store its item ID, amount, ground position and claim state with the gameplay owner. Use the existing nearby-item query or a pickup trigger for eligibility. Disable the solid collider or omit the simulated body once the remaining gameplay queries can find the coin independently. Keep a real contact solver for coins that must bounce off moving platforms or push each other.

On claim, reserve the item once, then follow the live target using the game's curve. Preserve the original award timing and decide what happens when the target disappears or the level unloads. Test two claimants in one tick, offscreen collection and reuse during flight. Compare active bodies and physics-step time at the same drop count, and verify the inventory delta for each case.

## Reuse an impact effect

Resolve damage and hit position in gameplay. Send the impact position, direction and variation to a persistent effect host. In a VFX Graph, one event can initialize the flash, debris and smoke systems or reusable subgraphs. Cache event/property IDs and a payload compatible with the assigned graph. Set each hit's attributes before sending. For distinct hits in the same frame, use a supported direct Event-to-Initialize path, supply `spawnCount`, and read each source position at initialization. Use a consistent simulation space so moving the next target leaves previous bursts in place. [VFX component API](https://docs.unity3d.com/Packages/com.unity.visualeffectgraph@17.0/manual/ComponentAPI.html) · [Unity's direct event example](https://discussions.unity.com/t/new-feature-direct-link/847493)

On a renderer without compute support, the built-in Particle System can reuse a world-space emitter per visual layer. For each hit, pass its world position in `ParticleSystem.EmitParams.position` to `Emit(emitParams, count)`. Moving the host for a later hit must preserve the earlier burst. [Particle System emission](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ParticleSystem.Emit.html)

Size particle capacity for overlapping bursts and their tails. Decide how visual overload degrades while every gameplay hit resolves. Split a host by region or use a bounded set of attached hosts when independent following, sorting or culling requires it. Give each region bounds that cover births and travel. On every supported renderer, test two different hits in one frame, a burst at the camera edge, and a target removed before the smoke clears. For a repeatable check, send red and green bursts to opposite sides of the screen before advancing the frame. Reuse the same payload, observe both colored regions on the one host, then verify both regions clear after the longest lifetime. Measure frame time separately at peak overlap. [VFX bounds and culling](https://docs.unity3d.com/Packages/com.unity.visualeffectgraph@17.0/manual/visual-effect-bounds.html)

## Reduce shader and VFX cost

1. Fix the camera, effect phase, simultaneous count and resolution. Locate the expensive draw, pass or dispatch on the target. Check transparent screen coverage and overlapping quads before rewriting shader math.
2. Change one cost at a time. Trim empty particle coverage, redundant layers or passes first when fill rate dominates. When shading dominates, remove repeated texture reads or noise octaves, bake invariant curves, or move suitable calculations to spawn or vertex work. A lookup can exchange arithmetic for memory traffic. Measure its effect.
3. Compare the original cue and GPU milliseconds under the same overlap. Check sorting at the character, silhouette, timing and the final fade. Keep the simplest version that meets the visual contract and measured budget on the supported backend.
