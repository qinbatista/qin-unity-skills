# ScriptableObject data contracts

## Design and review a data owner

For a new or changed SO, identify the domain, authored defaults, runtime writer, readers and lifetime. For each field, trace one production consumer and decide whether it belongs in the local file, the online representation, both or neither. Use these ten checks when reviewing an existing game.

| Rule | Design | Acceptance |
| --- | --- | --- |
| 1. Keyed lookup | Use a dictionary for searches by ID, including composite keys. Keep an ordered collection for authored order, UI traversal or the wire format. Where the project's serializer cannot round-trip the dictionary shape, serialize rows and build one nonserialized index per data revision. Reject empty or duplicate authored IDs before publishing an index. | Reimport the asset. Resolve **every** authored key and its expected value, a missing key and invalid authoring. Change a key and verify that the old index is invalidated. |
| 2. Value records | Use a small serializable struct for a distinct value with copy semantics, such as a spell's damage and duration in seconds. Keep reference identity, polymorphism and independently mutable objects with their appropriate owners. | Read both spell values from the saved asset. Change a returned copy where mutation is supported and verify the owned record still holds its original values. |
| 3. Used fields | Each serialized field must affect a named runtime, authoring, binding or migration operation. Trace getters through to their call sites. Check serialized paths, reflection, events, custom editors and existing saves before removing a field. A dormant idea can return with its first consumer. | Change a sentinel and observe its effect at that consumer. For a retired field, load the old asset and save, then verify the surviving keys and bindings. A getter or test assertion alone does not establish production use. |
| 4. One domain per asset | Give controller tuning, spell definitions, inventory and currency their own SO when their data has different writers or lifetimes. Several fields or record types can describe one domain. A bootstrap may reference those owners. | Identify the writer and lifetime of each group. Updating one domain must preserve the neighboring domain's asset and stored values. |
| 5. Local and online conversion | Define both persistence projections at design time. Persist an explicit selection of stable IDs and values in plain versioned data transfer objects (DTOs). Provide capture and apply operations for each supported format. [Local-first cloud saves](local-first-cloud-saves.md#implement-a-local-first-save) reuse the committed JSON when both projections contain the same data. A transient domain has an empty selection on both sides and needs no file or service call. | Read a real local file into a fresh instance. Verify the online payload and restoration through the selected adapter or decoder. Check the selected keys in each direction and the absence of temporary data, Unity object references and process-local IDs. |
| 6. Controlled access | Serialize private backing fields. Use getters, read-only views and validated domain methods for writes. Restrict setters to the actual writer. Return value copies or a genuinely read-only view when consumers could mutate backing storage. | Exercise a valid change, a rejected change and a boundary value such as zero. Check every write path and verify a reader cannot change the balance or catalog behind its owner's back. |
| 7. Shared state and behavior | Controllers and Managers that need common values bind the same domain SO or the same runtime instance of its asset. Put shared operations that depend on those values there, such as looking up a spell or crediting currency. Keep a script's private loop index, input sampling, scene binding, I/O and scheduling with their actual owner. | Drive a write through the normal caller. A second consumer must see the result directly through the shared SO. Check that neither consumer reaches through a peer Manager or Controller to access the value. |
| 8. Restart policy | Default mutable SO values to **session only**. Initialize one runtime copy from authored defaults per session or explicitly reset the shared instance. Restore only declared local fields, then apply a validated online snapshot according to the game's authority and revision policy. Distinguish missing data from an explicit zero. | End the session, create a fresh owner and recheck defaults, restored values and authored asset bytes. Exercise offline startup and online application. Use the project's disabled-domain-reload setting when supported. |
| 9. Compatible evolution | Keep stable keys, asset GUIDs and units. Assign defaults only to keys absent in an older version. For an authored field rename use `FormerlySerializedAs`. For local/online data retain the old decoder and migrate explicitly. Validate with the original schema and checksum before applying. Preserve unknown data or refuse the write. | A v1 wallet containing `coin = 37` loads with `coin = 37, money = 0`. Write v2, reopen it and verify both values. A malformed or newer file must survive failed loading, autosave and teardown byte for byte. |
| 10. Real compatibility replay | Run the actual Unity importer and the production serializer whenever a serialized field, key, type, unit, container or default changes. Use frozen bytes from the previous writer and isolated copies of receiving-game assets. | Compare old and current keys, values, GUIDs and bindings after reimport, save and fresh reload. For a failure identify the affected versions, keys and file, preserve the original and test a repair on a copy before enabling writes. |

Unity 6.6 supports native dictionary serialization. Check the exact Editor and wire serializer used by the receiving project, particularly for nested and non-string keys. The portable row example also works for projects that require a row representation. [Unity dictionary serialization](https://docs.unity.com/en-us/engine/6000.6/manual/programming-environment/code-reload-serialization/script-serialization/dictionaries)

## Spell catalog and player wallet

The [spell catalog](../assets/SOSpellCatalog.cs) owns authored `id`, `damage` and `durationSeconds`. Bind its asset to each spell consumer and call `TryGetSpell`. The returned struct supplies damage to the hit calculation and duration to the cast timer. The dictionary is built once on first use and rebuilt after deserialization or an Inspector edit. The shipped field name `castTime` maps to `durationSeconds` on reimport. The catalog and its index contribute no player save fields.

The [wallet](../assets/SOPlayerWallet.cs) uses the [local file base](unity-lifecycle-and-serialization.md#scriptableobject-local-files). Create one runtime wallet per player and bind both the reward producer and balance display to that instance. The producer calls `CreditCoins(amount)` and the display reads `Coin`. The storage owner checkpoints with `SaveDataAtLocal()` and flushes on retirement. Each example assumes a single active account and writer for its file. An account-switching game must scope that path and its online callbacks to the account.

| Representation | Keys | Apply policy |
| --- | --- | --- |
| Local wallet v1 | `version`, `coin`, `checksum` | Verify the v1 representation, keep coin and initialize money to zero. Load leaves the existing file in place until an explicit save. |
| Local wallet v2 | `version`, `coin`, `money`, `checksum` | Require both balances. Verify the compact writer layout and checksum before publishing the values. Unknown fields, unsupported versions and incompatible encodings leave the original available for recovery. |
| Online full wallet | `version`, `coin`, `money` | `CaptureOnline()` returns the transport DTO. `ApplyOnline(json)` requires both balances and accepts explicit zero. A partial response leaves both values intact. A service using patches needs explicit field presence and a merge against the accepted revision. |

The on-disk checksum detects accidental changes. The game's service adapter owns authentication, account matching, revision conflicts and transport. The fixture exercises conversion without contacting a service. The default `SOLocalData` serializer signs the concrete SO layout. A shipped subclass using that format needs a reader for its original representation before changing that layout. The example wallet's v1 format applies only to files produced by its v1 writer.
